# Improvement Ticket Template

Linear issue description format for an Improvement (an existing thing made better).
A real improvement names the current workflow, the concrete pain, and ideally a
measurable target — not "optimize the workflow."

```markdown
## Summary

[Brief plain-English summary of the improvement.]

## Issue Type

Improvement

## Current Workflow

[How it works today — specifically.]

## Pain Point

[What is slow, confusing, error-prone, manual, or inefficient. Quantify if
possible: how many steps, how long, how often, what error rate.]

## Proposed Improvement

[The desired improvement.]

## Expected Benefit

[Operational, technical, user, or business benefit.]

## Success Criteria

- [ ] [Measurable where possible: fewer clicks, faster load, lower error rate,
      less manual work.]
- [ ]
- [ ]

## Affected Area

- Product area:
- Page/screen:
- User role affected:
- Environment:

## Risk / Complexity Notes

[Known risks, dependencies, or implementation concerns. If complexity is unknown
enough to block estimation, consider a Spike first.]

## Priority Recommendation

[Urgent / High / Medium / Low]

## Open Questions

- [Only unresolved questions that matter.]
```
